# 岗位知识库问答：检索策略评测

用 410 条真实招聘 JD 搭一个可评测的 RAG 问答，把「切段长度」和「召回条数」当成两个可量化的变量跑消融。

**一句话结论：切段从「不切」改到 300 字，输入 token 降 63%，但生成耗时几乎不变（2.2 s 恒定）——瓶颈在模型侧，不在上下文长度。**

## 效果

| 指标 | 结果 | 说明 |
|---|---|---|
| 20 题总分 | 19 / 20 | A 9/10、B 5/5、C 5/5 |
| 平均输入 token | 870 | 不切段时 3046 |
| 检索耗时 | 2–4 ms | 纯 CPU BM25，无 GPU、无向量库 |
| 生成耗时 | 0.9–2.3 s | 波动来自模型侧，与上下文长度无关 |

题分三类，答案都写死在 `data/questions.json` 里，判分脚本自动跑：

- **A 类（10 题）**：答案在语料里，看能不能捞到并算对（例：出现频率最高的五个技能）
- **B 类（5 题）**：语料里没有，看会不会老实拒答（例：字节跳动杭州办公室在第几层楼）
- **C 类（5 题）**：语料只写了一半，看会不会承认不确定（例：没写学历要求是不是就不卡学历）

## 实验一：切段消融（0 / 300 / 500）

同一查询、同一 top-k、同一模型，只改切段长度：

| 切段 | 上下文 | 输入 token | 检索 | 生成 |
|---|---|---|---|---|
| 不切 | 4951 字 | 3046 | 192 ms | 2181 ms |
| **300 字** | **1586 字** | **1138** | 287 ms | 2219 ms |
| 500 字 | 1851 字 | 1310 | 223 ms | 2259 ms |

三条结论：

1. 切 300 后输入 token 降 63%，但**生成耗时几乎不变**——上下文变短省的是钱，不是时间。
2. 质量上 300 最好：能命中具体技术细节（RAG 链路、切片、向量化、重排）；不切段会整段糊进来，广告语都混进答案。
3. 切 500 时同一岗位的多个片段会占满名额，答案退化成技能清单——所以加了 `--max-job` 限制同岗位最多取几段。

## 实验二：同一实验，平台版 vs 代码版

同一个 Coze 对话流也跑了一遍同样的题，两边对照：

| 维度 | Coze 平台版 | Python 代码版 |
|---|---|---|
| A 类答对 | 6/10 → 8/10 → 9/10（三轮手调 top-k） | 9/10（一次跑完） |
| B 类拒答 | 5/5 | 5/5 |
| 平均输入 token | 1629 | 870 |
| 检索耗时 | 295 ms | 2–4 ms |
| 能改什么 | 提示词、top-k | 换检索算法、加权重、改判分、批量扫参数 |

两边最终打到同一水平，但代码版能**定位到平台版查不出的问题**（见下文），而且成本低一半。

## 已知问题（重点）

这四条是跑出来的，不是猜的：

1. **IDF 坍塌**：`明确写 Python 的岗位有多少条` 这题两边都错。原因是 Python 出现在 193 条 JD 里，IDF 趋近 0，统计段在打分上永远排不过普通 JD 段。调大 top-k 治不好，得按字段建索引或做混合检索。
2. **跨文档失败**：`哪类岗位更强调 RAG，举一个具体岗位例子` 答不出具体岗位——统计在汇总文档，岗位名在明细文档，一次检索只能命中一边。
3. **判分器有偏差**：规则判分只查关键词和数字，答对了但换个说法可能被误判。19/20 是「按这套规则算 19」，不是绝对真值。
4. **语料噪声**：实习僧页面正文里混进过 JS/JSON 碎片（`"event_id":"lesson_"`），已用 `clean_text()` 清洗，但清洗本身也可能误删。

## 目录

```

  config.py        路径、模型参数、提示词、判分阈值
  corpus.py        读语料、清洗、切段（含统计汇总单独入库）

  generate.py      拼上下文、调 DeepSeek API
  judge.py         规则判分（A/B/C 三类各一套）
  build_questions.py  20 题 + 标准答案 + 判分规则（生成 data/questions.json）
data/questions.json  题库

inspect_retrieval.py 排查某条查询为什么排成这样
tools/build_report.py 把结果导成 xlsx 对照表
```

## 语料

410 条杭州 AI 岗位 JD，来自 5 个渠道（24365 国家大学生就业服务平台、实习僧、51job、BOSS 直聘截图、手工精读），已去重、剔除销售/硬件/算法另一赛道，按岗位方向分成 10 份文档。语料本身不在仓库里（含公司联系人信息），脚本里留了 `RAG_CORPUS` 环境变量可指到自己的数据。

## 为什么做这个

不是想做一个问答机器人，是想搞清楚「同一个问题，换个检索参数，效果差多少」——这件事有标准答案、能复现、能说清边界，比做一个看起来聪明但讲不清的 demo 有用。

---

模型：DeepSeek `deepseek-chat`，temperature 0.3；检索：BM25 + 中文 bigram，无外部向量库。
